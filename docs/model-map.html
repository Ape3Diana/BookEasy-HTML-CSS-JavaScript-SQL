BookEasy — model & API map

What the mock holds, which function answers which endpoint, and what is still missing. Current as of the employees + price-snapshot change. Update this when the model changes.

1. Tables

Six tables in the mock, plus one designed but not modelled yet.

TableColumnsNotes
users id · email · password · fullName · role · createdAt role is client or admin. Email unique. Password becomes a bcrypt hash in 2.3 and never leaves the server.
services id · name · description · durationMin · price · isActive · createdAt Soft delete via isActive. Duration 15–240 and a multiple of 15; price ≥ 0.
employees id · fullName · isActive · createdAt new Inactive = left the salon; never offered, but kept so old bookings still resolve a name.
employeeServices employeeId · serviceId new Link table, many-to-many. Composite PK in SQL. A service exists once; several people can perform it.
workingHours id · weekday · opensAt · closesAt Salon-wide; everyone works these. opensAt = null means closed. Bounds the slot grid, nothing else.
bookings id · userId · serviceId · employeeId · price · startsAt · endsAt · status · createdAt · cancelledAt price is a snapshot written at creation, never recomputed. status ∈ pending, confirmed, completed, cancelled.
booking_slots bookingId · slotStartsAt Partea 2 Not in the mock by design. Its unique key must become (employee_id, slot_starts_at) — see the open questions.

Fields that are not columns

Every booking also carries serviceName, employeeName, userFullName and userEmail. These are JOIN results, not stored data — the API sends them glued on so a page never has to look across tables. price looks similar but is the opposite: a real column, frozen at sale time, so changing the price list cannot rewrite past revenue.

3. Internal helpers — no endpoint, and that is correct

These are the parts of the mock playing server, not API. In Partea 3 they do not become fetch calls — they disappear from the frontend entirely.

getUserById / getUserByEmail

Steps inside login and register. Not exported — their rows still carry the password.

getEmployeeById / employeeCanDoService

Used by addBooking and the slot grid. Return null / a boolean, never throw.

getWorkingHoursFor(weekday)

Only the slot calculation needs it, and that moves to the server in 2.5.

getActiveBookingsForDay

Feeds the slot calculation. Throws if the employee id is missing, rather than silently meaning "everyone".

countActiveFutureBookings

RB-07, checked before the insert; becomes a 422 on the server.

clone / cloneAll / nextId / dayAt

Plumbing. dayAt is replaced by seed.sql in Partea 2.

setCurrentUserId / readStoredUserId

The session, kept in localStorage inside the module so it survives navigation and no page touches storage. Dies entirely in Partea 3 — the cookie is httpOnly.

Each renderer checks for its own slot. renderFooterHours() returns early when the page has no #working-hours, so login.html and register.html get a header and no footer without a flag saying so. The markup decides what chrome a page has; the page module only says initLayout().
Logging out is not just a header change. account.html is showing someone's bookings and service.html offers a confirm button only to a logged-in client, so both must redraw. layout.js dispatches bookeasy:session-changed on document after logout(); pages that show private data listen, the rest ignore it. An event rather than a direct call because layout.js is imported BY the pages — it must not know which of them exist.

4c. Persistence — the mock's "database file"

Every page load re-imports mock-data.js, which rebuilds the tables from the seed. Without persistence a user who registered on one page would not exist on the next — and the Partea 1 checkpoint (register → login → rezervare → cont → admin) is five pages, so five reloads.

KeyHoldsNotes
bookeasy.stateusers, services, bookings, workingHours Written after every writer. Carries seededOn; state from another day is discarded, because the fixtures are relative to today and would otherwise rot overnight.
bookeasy.userIdthe session Only an id — the role is looked up from the data, never stored. Forgeable in DevTools, which is the point: Pas 2.3 replaces it with an httpOnly cookie.
bookeasy.test.*the same, for the smoke test smoke-test.html sets window.__BOOKEASY_TEST__ in a plain <script> (which runs before deferred module scripts), so a test run cannot leave its fixtures in the app's data.

employees and employeeServices are deliberately not persisted — nothing can change them until an admin screen exists. resetMockData() restores the seed in memory and logs out.

5. Business rules — where each one is enforced

Most rules have two enforcement points: the UI must not offer the invalid thing, and the writer must refuse it anyway. The rule itself is defined once, in rules.js.

Intervals are half-open: [start, end). A booking that ends at 12:00 does not collide with one starting at 12:00, so appointments can run back to back. Treating the boundary as a clash would cost the salon one usable slot after every single appointment. Two smoke-test checks pin it, and it is why a 60-minute service is offered at 12:00 when the next booking starts at 13:00 — an exact fit.
The grid shows START times, greyed out when unusable. A slot can be grey for two different reasons: the hour is inside an existing booking, or the hour is free but the service would run past the next one — a 60-minute service at 09:15 when 10:00 is booked. Both render identically on purpose: "grey means you cannot pick it" is one rule a client learns at a glance, where explaining the arithmetic would not help. It also means the same day looks different for a 30-minute service than for a 120-minute one.
The dashboard uses three different definitions of "which bookings count", on purpose. rezervări active counts pending + confirmed — the two that still hold a slot. Grad de ocupare counts everything except cancelled, because a completed appointment did use the chair. Venit realizat counts completed only, because that is the money actually earned. They look inconsistent side by side; unifying them would break at least one.
Revenue on a day the salon is now closed is a real state, not a bug. RB-08 only protects future active bookings, so an admin may close Sundays after the salon has already completed Sunday appointments. The revenue tile is then correct and the occupancy tile shows —, because there are no opening hours to divide by. Both are right; the pair only looks odd.
Occupancy for past days is only as good as the data behind it — and the data has no memory. working_hours stores the schedule as it is now, so "how busy were we on 30 August?" cannot be answered once the schedule changes. Inferring the day's span from its own bookings would be circular: the denominator would come from the numerator.

Doing it properly needs a per-date snapshot rather than a weekly template — the same reasoning that put price on the booking row:

salon_days — date PK · opens_at · closes_at · staff_count

working_hours would stay as the template the admin edits, used to generate future salon_days rows; once a date passes its row is history and never changes. That table would also make holidays and one-off closures expressible, which a weekly template cannot do at all — it can say "closed on Thursdays", never "closed on 25 December".

Not built. getOccupancy returns null for a closed day, which is honest: the system does not know. A design note for the mentor, and a Partea 2 schema decision.

7. Open questions for the mentor

  1. booking_slots must change key. UNIQUE(slot_starts_at) would forbid two employees from working the same hour. It has to become UNIQUE(employee_id, slot_starts_at).
  2. The two added service endpoints — GET /api/admin/services and GET /api/services/:id — are missing from Anexa B.
  3. GET /api/working-hours (public) — Anexa B only has the admin route, but the footer shows the programme to visitors.
  4. The two added employee endpoints — GET /api/employees and GET /api/services/:id/employees.
  5. Pagination envelope field names: items / total / page / pageSize.
  6. Errors thrown, not returned — confirm api.js will throw in Partea 3.
  7. price cast to a number server-side in 2.4, so DECIMAL does not arrive as "120.00".
  8. Field naming: the mock is camelCase, SQL is snake_case. Partea 2 must alias or map.
  9. Grad de ocupare — definition still undecided.
  10. Admin management of employees — no CRUD exists. Is it in scope?

7b. Conventions worth keeping

ConventionWhy
One state object, one render() Every handler updates state and redraws. Stops the service page's confirm panel showing an hour that belongs to a specialist you have since switched away from.
One listener per container, not per row Rows are replaced on every render, and a listener on a replaced node dies with it. Events bubble, so the container sees them all — including rows added later.
Re-read after a write, never patch the DOM by hand cancelBooking returns nothing (204). Re-rendering from the data updates the badge, the button and the note together, and is what the page will do over the network anyway.
State in data-*, not in a parallel class aria-pressed for the pickers, data-status for the badges. One assignment drives both the look and what a screen reader announces, so they cannot disagree.
"Not logged in" ≠ "nothing here" A visitor on account.html gets a prompt to log in, not an empty list.

The slot grid gets SIMPLER, not harder. Today service.js calls getWorkingHoursFor + getActiveBookingsForDay + calculateDaySlots. In Partea 3 that is one await api.getAvailability(serviceId, employeeId, date) — the server does the work, using the same availability.js.
A client may hold two bookings at the same time, with different employees. Deliberate. RB-02 is per employee and RB-07 counts bookings rather than overlaps, so nothing prevents it — and nothing should. Parallel services are ordinary salon practice: a manicure while hair colour develops is two employees and one client at the same hour. The client knows their own schedule; the salon only needs to know that each employee is in one place at a time, which is exactly what RB-02 guarantees.

10. Known limits

LimitWhy it is acceptable now
Two tabs overwrite each other's writes Persistence saves the whole state blob, so the last tab to write wins. A booking made in another tab can be lost. Partea 2 has one database and real transactions; here it is the cost of a fake one.
A service can be withdrawn while future bookings exist Deliberate: those appointments still happen, and the booking carries its own serviceName and price. Unlike RB-08 for hours, nothing needs to be refused.
Deactivating an employee is not guarded No screen manages employees yet. When one exists it needs RB-08's treatment: future bookings must be moved first.
A page left open past midnight drifts TODAY is captured when the module loads. Reload after midnight.
Occupancy for past days assumes the schedule never changed See the salon_days note above.

12. Which layer enforces what

Every rule sits in exactly one of three places, and the choice is not arbitrary — it follows from what each layer is capable of expressing.

LayerRulesHolds against
The database
Partea 2		 UNIQUE(email) · UNIQUE(employee_id, slot_starts_at) · CHECK (duration_min BETWEEN 15 AND 240) · CHECK (price >= 0) · CHECK (closes_at > opens_at) · foreign keys everything, including direct SQL and a bug in the server
The server
rules.js, moved		 RB-02 · RB-03 · RB-05 · RB-06 · RB-07 · RB-08 · "an admin cannot book" · registration and service validation anything arriving through the API — which is every real client
The page which slots are offered, which buttons exist, which fields show a message nothing. It is courtesy: it stops mistakes, never attacks
Why a rule cannot always live in the database. SQL constraints describe one row, or one column's uniqueness. RB-08 — "no future active booking may fall outside these hours" — is about relationships between rows over time, and no CHECK can express it. Same for RB-07 (count the client's future bookings) and RB-03 (compare against now). Those need code, and code means the server, and the server is reachable only through the API.
What that means for direct database access. A hand-written UPDATE employees SET is_active = false bypasses every rule in the middle row — Ana's future bookings would be orphaned with no warning, because no code ran. That is normal and accepted: the schema still holds (foreign keys, uniqueness, checks), and direct access is a privilege given to people expected to know what they are breaking. It is also why the app is safe without an employee guard today: nothing in the app can deactivate an employee, so there is no code path to protect. The guard becomes necessary the day an admin screen can.
